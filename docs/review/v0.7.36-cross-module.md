## 1. Tier 1 — 架构层

### Finding 1.1：`registry.UserAgent` 是名义上可写的全局变量

**位置**: `internal/registry/client.go:22`

```go
var UserAgent = version.UserAgent
```

值是 `version.UserAgent`（const），但用 `var` 重新声明。Go 允许任何包写 `registry.UserAgent = "x"`。当前 8 个 set 点（`client.go:64,207,238`; `bearer.go:152`; `inventory.go:315`; `blob.go:72,203,238`）都是读取，**实际无写者**。

**触发条件**: 任何包在未来某个路径上误写。

**影响**: 违反 `version.UserAgent` 的 const 约束，把全局常量降级为可变状态。同包 `SyncUserAgent` / `ProbeUserAgent`（`version/version.go:55-58`）正确用 const —— 同一仓库内的纪律不一致。

**修法**: Go 不支持 `const X = imported.const`，两种等价路径：
- 路径 A（最简）：删掉 `client.go:22` 的 `var`，让所有调用点直接用 `version.UserAgent`（已经是 8 个 set 点的引用真相）
- 路径 B（折中）：保留本地 `var`，加 `//nolint:unused` 或文档化"任何人不得修改此 var"，但这等于无保护

推荐路径 A。

### Finding 1.2：`time.Duration` 字面量散落 11 处，1 处语义重复

**位置**:
- `internal/server/server.go:284-287`（HTTP server 超时 10s/30s/120s）
- `internal/server/server.go:339`（events flush 5s）
- `internal/server/server.go:351`（proxy probe 60s）
- `internal/server/server.go:394`（**GC 周期 24h**）
- `internal/server/server.go:396`（GC 启动延迟 30s）
- `internal/server/server.go:415,432,444,475`（shutdown / cleanup ×4 各 30s）
- `internal/pull/queue.go:448`（单点 timeout 5s）
- `internal/pull/executor.go:68`（layer 下载超时 15min）
- `internal/storage/filesystem.go:844`（**upload session 截止 24h**）

**触发条件**: 用户想把"全站超时放长"或"GC 周期改短"，必须跨包 grep。

**影响**: 同一语义（24h）在 `server.go:394` 和 `filesystem.go:844` 各写一次。**这意味着改一处行为变了，另一处不会跟着变** —— 例如把 GC 周期从 24h 改成 12h，upload session 截止仍 24h，资源错配。

**修法**:
- 引入 `config.Mutable.Timeouts`（GCInterval / UploadSessionTTL / ShutdownGrace / EventsFlushInterval / ProxyProbeInterval / PullLayerTimeout），全走 UI 配置
- 容器内编译期常量走 `config.Config.Timeouts`（无 UI 配置需求的部分）
- 至少把"同一语义"的两处收敛到一处常量（`storage/filesystem.go:844` 和 `server.go:394` 的 24h 必须统一来源）

### Finding 1.3：`internal/api` 是隐性 god 包，71 个 HTTP 端点按 receiver 而非按业务域切片

**位置**:
- `internal/api/handlers.go` — `*Handlers`，8 个方法
- `internal/api/handlers_extra.go` — `*ExtraHandlers`，**48 个方法，2038 行**（全仓最大单文件）
- `internal/api/sync_handlers.go` — `*SyncHandlers`，15 个方法
- 合计 ~71 个 HTTP 端点；outbound=29（全仓最大）

**触发条件**: 新增一个端点时，需要先判断"放哪个文件 / 哪个 receiver"。

**影响**: 文件名是按"放满了拆出来"演化出的，不是按业务域。新人加端点时心智负担大；3 个 receiver 之间的字段复用靠 `Handlers` 嵌入（推测），可能存在隐性耦合。**未来按 bounded context 拆分时这里是最大杠杆点**，越晚拆代价越高。

**修法**: 不强制现在就拆（broad refactor, code-review skill 不报此类），但作为下次大版本的预告：
- 按 bounded context 拆：`internal/api/browse/`、`internal/api/credentials/`、`internal/api/pull/`、`internal/api/sync/`、`internal/api/settings/`、`internal/api/stats/`、`internal/api/proxies/`
- 每个子包暴露 `Mount(r chi.Router)`，由 `api.NewRouter` 当 facade 装入
- 当前 `*Handlers` / `*ExtraHandlers` / `*SyncHandlers` 三个 receiver 拆成独立的 dependencies（不再交叉依赖）

### Finding 1.4：`Sync.Engine / Store / Writer` 与 `credentials.Vault` 全部缺接口

**位置**:
- `internal/sync/engine.go:68` `type Engine struct`
- `internal/sync/store.go:23` `type Store struct`
- `internal/sync/writer.go:43` `type Writer struct`
- `internal/credentials/credentials.go:76` `type Vault struct`

**触发条件**: `internal/api/sync_handlers.go` 的端点单测需要 SQLite 真库 + 真文件 IO。

**影响**: 单测被迫走真 IO，跑得慢且脆弱；将来要做"离线 sync / dry-run sync / fake vault 测试"会被迫加接口。**仓库里 `pull/executor.go:641` 的 `manifestFetcher` 是 consumer-defined 接口的好例子**，证明作者懂这一原则，但只在"必要处"用。

**修法**: consumer-defined 最小接口：
```go
// in internal/api/sync_handlers.go
type taskStore interface {
    GetTask(ctx context.Context, id int64) (*sync.TaskRow, error)
    InsertRun(ctx context.Context, ...) (int64, error)
    // ...
}
```
每个端点需要的方法只列所需面（interface segregation）。这样测试用 fake 实现即可，不需要真 SQLite。

不强制现在做（单 impl 时属于"过度设计"），但**新写 sync / vault 测试时如果发现要 mock，先补接口再写测试**。

## 2. Tier 2 — 代码层

### Finding 2.1：`pull/queue.go:507` 用 `%v` 而非 `%w` 把 panic 转 error

**位置**: `internal/pull/queue.go:507`

```go
err = fmt.Errorf("internal error: %v", r)
```

**触发条件**: caller 想 `errors.Is(err, ErrSomething)` 区分 panic 来源与业务错误。

**影响**: panic recovery 的错误链断了 —— `%v` 不支持 `errors.As`。仓库内绝大多数 `fmt.Errorf` 已正确用 `%w`（见 evidence §6）。

**修法**: 改为 `fmt.Errorf("internal error: %w", r)` 或定义专门的 `PanicError` 类型并实现 `Unwrap()` 返回 `r.(error)`。如果 `r` 不是 error（如 string），走定义 recovery error 类型路径。

### Finding 2.2：`sync/writer.go` 自实现 `itoa` 替代 `strconv.Itoa`

**位置**: `internal/sync/writer.go:293`

```go
// itoa avoids importing strconv just for two call sites.
func itoa(n int) string { ... }
```

注释自己写"省 strconv import"。

**触发条件**: 任何 reviewer 看到自实现 itoa 都会停下来想"为啥不直接用标准库"。

**影响**: `internal/sync/store.go` 已经在用 `strconv`（详见 `sync` 包的 import 块）—— 这一节省的"避免 import"前提不成立。代码气味。

**修法**: 删 `itoa` 函数，调用点改 `strconv.Itoa`。

## 4. 正面观察（值得保留的纪律）

- **零循环依赖**（双向对扫验证，见 evidence §3）
- **env 读取集中**: 5 处全部在 `config/config.go` 或 `cmd/server/main.go`，业务配置全部走 UI SQLite（AGENTS.md §"v0.5.9 起"已贯彻）
- **`%w` 包装纪律好**: 绝大多数 `fmt.Errorf` 用 `%w`，仓库内 19 处 `errors.Is` 能解开
- **SCHEMA_VERSION append-only**: 当前 v14，14 条迁移严格遵守"同 commit"纪律（AGENTS.md §"改 schema 的纪律"）
- **cmd/server/main.go 仅 import 3 个包**（`config` / `server` / `version`）—— "main 极薄、靠 Build 装配"纪律生效
- **9 个包级 var 全部 init 后只读**（evidence §9）—— 无运行时并发写入风险（除 §1.1 的 UserAgent）
- **chi 路由唯一**（3 个 import：`api` / `docs` / `registryd` / `server`）—— AGENTS.md §"单进程单二进制"纪律
- **storage / db / config / version / credentials** 是合理的 inbound 高频（5/5/4/4/4），没有 inbound > 5 的 god package
